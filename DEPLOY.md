# Деплой на awwwdde.art

Проект подготовлен по инструкции `C:\Users\Inv\source\vscode\vlad\GUEST.md`.

## Архитектура одного контейнера

```text
Caddy / HTTPS (платформа)
       |
       v
Next.js / 0.0.0.0:8080
       | /api/*              | /healthz
       v                    v
FastAPI / 127.0.0.1:8100 ----+
       |
       v
PostgreSQL 16 (платформа, DATABASE_URL)
```

`scripts/serve.py` запускает оба процесса, передаёт завершение обоим и останавливает контейнер, если один из сервисов упал. Python API не слушает внешний интерфейс. На старте FastAPI выполняет `alembic upgrade head`. Next.js `/healthz` проверяет доступность внутреннего API, не обращаясь к внешним сервисам.

## Соответствие контракту

- `Dockerfile` находится в корне.
- Единственный внешний порт: `0.0.0.0:8080`.
- `GET /healthz` → 200, когда оба сервиса готовы.
- В runtime-образе установлен `curl`.
- Next.js собирается в `standalone`.
- Builder и runner используют совместимый Debian Bookworm, чтобы нативный Sharp работал в runtime.
- Node.js 22 копируется из builder в Python runtime, вместо старого системного Node.
- В production нет SQLite fallback: без `DATABASE_URL` запуск завершается ошибкой.
- Обращения и лимиты хранятся в PostgreSQL, миграции применяются автоматически.
- Файлы `.env`, локальные данные, node_modules и venv в образ не копируются.
- Нет принудительного HTTPS-редиректа. HTTPS обслуживает Caddy.
- Нет требования к docker-compose, дополнительному контейнеру приложения или фоновой очереди.

Кэши Next.js являются восстановимыми; приложение не полагается на их сохранение между деплоями. Авторские файлы находятся в образе как статические ресурсы. Загрузка пользовательских файлов в этой версии не предусмотрена.

## Переменные

Платформа предоставляет:

| Переменная | Использование |
|---|---|
| `DATABASE_URL` | PostgreSQL; стандартный `postgresql://` преобразуется в драйвер `postgresql+psycopg://` |
| `PUBLIC_SITE_URL` | Адрес сайта для sitemap и метаданных; читается при запросе |
| `SECRET_KEY` | HMAC-ключ хеширования почты в rate limit |
| `JWT_SECRET` | Этой версии не требуется |

Дополнительно в панели можно задать `ADMIN_API_TOKEN` — длинный случайный секрет для чтения обращений. Без него endpoint закрыт для всех. Не добавлять секреты в Git, Dockerfile и клиентский JavaScript.

## Проверка контейнера перед публикацией

При запущенном Docker Engine:

```powershell
docker build -t roman-koskin .
# Задайте DATABASE_URL до запуска (тестовая PostgreSQL должна быть доступна контейнеру).
docker run --rm --name roman-koskin-check -p 8080:8080 -e DATABASE_URL -e PUBLIC_SITE_URL=http://localhost:8080 -e SECRET_KEY roman-koskin
```

В другом терминале:

```powershell
curl.exe -fsS http://localhost:8080/healthz
docker exec roman-koskin-check sh -c "command -v curl"
```

На Docker Desktop хостовая PostgreSQL обычно доступна через `host.docker.internal`; не использовать `localhost` в `DATABASE_URL` для базы на хосте.

Для локальной проверки именно production-сборки без Docker можно запустить Python API на 8100 и `npm run start` после `npm run build`. Команда `npm run start` слушает `0.0.0.0:8080`; для полного standalone сценария статику нужно скопировать в `.next/standalone` как в Dockerfile.

## Настройка платформы

1. Источник — папка проекта `C:\Users\Inv\source\vscode\koskin` либо Git-репозиторий с этими файлами. При папочном источнике путь должен быть доступен машине платформы.
2. Slug — например `roman-koskin`.
3. Платформа собирает корневой Dockerfile, создаёт PostgreSQL и передаёт переменные.
4. Приложение применяет миграции и начинает отвечать на `/healthz`.
5. Внешний адрес выдаётся платформой, например `https://roman-koskin.awwwdde.art`.

## Чтение заявок

После задания `ADMIN_API_TOKEN`, из доверенного терминала:

```powershell
$headers = @{ Authorization = "Bearer $env:ADMIN_API_TOKEN" }
Invoke-RestMethod "$env:PUBLIC_SITE_URL/api/admin/enquiries?limit=50&offset=0" -Headers $headers
```

Заявки доступны в `/admin`: поиск, статусы и ответ через почтовое приложение. Автоматические уведомления по почте/Telegram пока не подключены.

## Вход и CMS

Перед публикацией создайте хеш пароля (пароль вводится скрыто):

```powershell
.venv\Scripts\python.exe scripts/setup-admin.py --hash
```

В панели платформы задайте `ADMIN_USERNAME=roman` и `ADMIN_PASSWORD_HASH` равным выведенной строке целиком, включая символы `$`. Минимум 12 символов в пароле. Не добавляйте исходный пароль или хеш в репозиторий. `.data/admin.json` предназначен только для локальной разработки и не попадает в образ. Если хеш не задан, production-вход закрыт. Смена хеша отзывает старые сессии.

На HTTPS сессия использует Secure/HttpOnly/SameSite=Strict cookie и живёт 8 часов. Миграция `0002` добавляет статусы, CMS, сессии и изображения; начальные проекты импортируются только при первом запуске, существующий контент не перезаписывается. Кнопка «Сохранить» применяет изменения без сборки. Черновики не выдаются публичным API и отсутствуют в sitemap. Обложки и галерея хранятся в PostgreSQL, поэтому переживают пересоздание контейнера. Включайте таблицу media в резервные копии БД. Изображения доступны по публичным URL: не загружайте конфиденциальные материалы.

Проверка после деплоя: вход по HTTPS → создать черновик → загрузить обложку → сохранить → убедиться, что черновика нет на сайте → опубликовать → проверить страницу проекта → выйти и убедиться, что `/api/admin/content` отвечает 401.

## Предел проверки в текущем окружении

Docker CLI установлен, но Docker Engine при разработке не был запущен. Поэтому сборка образа, запуск контейнера и интеграция с PostgreSQL платформы требуют отдельного smoke test. Локальные API-тесты используют изолированную SQLite; production Secure cookie требует проверки на HTTPS платформы.
